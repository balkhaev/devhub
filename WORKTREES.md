# Worktree, локальный stage и выпуск

Основная папка каждого репозитория — интеграционный стенд на локальной ветке `stage`.
DevHub запускает серверы только из неё или её пакетов. Изменения из worktree видны
в приложении после интеграции в `stage`. Production собирается и запускается
собственными командами проекта.

## Общий порядок

1. Прочитать `AGENTS.md` и `.devhub/worktree.json` основной папки. Сначала проверить
   существующие worktree и переиспользовать подходящую рабочую ветку.
2. Создать задачу от чистого `stage`: `bun run worktree create orders-filter`.
   Получится ветка `codex/orders-filter` в `.worktrees/<project>/orders-filter`.
   В Python-проекте: `bun D:/code/devhub/src/stage.ts create orders-filter --project D:/code/project`.
3. Работать и коммитить в рабочей ветке. Локальные тесты там полезны; финальные
   проверки проходят в основной папке. Dev-команды из worktree обращаются к
   основной папке и показывают уже интегрированный код.
4. В основной папке выполнить `bun run worktree integrate codex/orders-filter`.
   Команда требует чистые исходную и основную папки, делает merge в `stage` и
   запускает `checks` из `.devhub/worktree.json`. Конфликты остаются для решения;
   провал проверок оставляет изменения в stage и не создаёт отметку успешной проверки.
5. Открыть приложение через DevHub, выполнить ручную проверку поведения на этом
   стенде. После последней правки повторить `bun run worktree check`.
   `bun run worktree status` показывает `checked` и `releaseReady`.
6. Выпускать в указанную `releaseBranch` только в задаче, которая разрешает выпуск,
   после успешной финальной проверки чистого `stage`. Проверить обычную сборку,
   production entrypoint и требования конкретного проекта. Push и deploy
   запускаются отдельно; интегратор их автоматически не выполняет.
7. Завершённый обычный worktree убрать через `bun run worktree finish <полный путь>`.
   Удаление возможно только внутри разрешённого `worktreeRoot`, после успешной
   проверки stage, когда коммиты уже влиты и нет tracked, untracked или ignored
   файлов. Приватные файлы и данные сначала сохранить. Ветка остаётся.
   Codex-managed worktree архивировать через приложение, сохраняя привязку чата.

## Защита локальной работы

При первоначальной настройке `stage` создан от текущего HEAD основной папки;
файлы и индекс сохранены. Имеющиеся незакоммиченные изменения не считаются
автоматически готовыми к выпуску. Перед новой интеграцией их нужно проверить и
сохранить в соответствующей рабочей ветке. Интегратор откажется смешивать их с
другой задачей. Он не выполняет reset, массовый stash, force remove и слияние всех
исторических worktree.

Отметка проверки относится к HEAD, ветке, исходникам, untracked файлам, списку
команд и локальным env-файлам корня/пакетов `apps`. Она аннулируется при изменении
этих входов. Артефакты моделей, содержимое баз данных и внешних сервисов не входят
в отметку; ручная проверка приложения и требования проекта остаются обязательными.

`.state/stage` содержит локальные отметки и блокировки операций. Если проверяющий
процесс был принудительно завершён, проверить PID в `.lock` и убедиться, что он
уже не работает, прежде чем удалить его блокировку.

## Подключение нового проекта

`devhub.json` описывает исходные команды приложения, пакеты внутри основной папки,
порты и зависимости. `.devhub/worktree.json` содержит `version: 1`,
`stageBranch: "stage"`, проверенную `releaseBranch`, массив `checks` и относительный
`worktreeRoot` вне основной папки. Пустой список проверок запрещает финальную
валидацию. Команды `checks` должны проверять, а не исправлять исходники или
публиковать приложение.

Обёртки `launch.cjs` и `worktree.cjs` находят DevHub через `DEVHUB_ROOT` или
`~/.devhub.json`. Политику и обёртки нужно включить в baseline stage, чтобы новые
worktree наследовали их. Сначала `bun run stage init --project <путь>`, затем
подключение через каталог DevHub. Linked worktree автоматически исключены из
каталога. Старые самостоятельные копии перенаправляются полем `aliases` в
`services.json`; их файлы сохраняются для восстановления.

Обновлённые общие правила имеют приоритет над прежними указаниями сразу работать
в main, автоматически пушить изменения и принудительно удалять все worktree.
