# Пульт

Одна страница, откуда запускаются серверы разработки всех проектов на этом компьютере и открываются
их веб-интерфейсы: MediaPipes, студия сцен Montage, Inference, Modeler, Luv Club, Алтай и остальные.

## Настройки и база знаний

«Порядок» и «Прод» находятся в «Настройках». Старые ссылки `#/tidy` и `#/prod`
продолжают работать. В каждом проекте доступны вкладки «Проект», «Canvas», «Kanban»;
доски также открываются маленькими кнопками ◇ и ▥ рядом с названием проекта
слева. Кнопки остаются доступны, когда список сервисов проекта свёрнут.

- **Canvas**: заметки, процессы и решения с полным текстом, цветами, размерами и
  координатами. Блоки перетаскиваются, соединяются направленными подписанными связями;
  есть масштаб и перемещение поля. Координаты можно изменить с клавиатуры в редакторе.
- **Kanban**: колонки, карточки с описаниями и метками, перенос между колонками и
  изменение порядка перетаскиванием или кнопками. Колонку также можно выбрать в редакторе
  карточки. Заполненную колонку нельзя удалить.
- Поиск на каждой доске использует заголовки и полный текст, у карточек также метки.
  Markdown и URL хранятся как текст; HTML не выполняется.

Данные общие для интерфейса и MCP. Они хранятся в SQLite
`F:/AI/devhub/knowledge.sqlite` (при настройке `data` в `services.json` — в
`<data>/devhub/knowledge.sqlite`), вне Git и временных worktree. Ключ проекта — его
канонический путь: переименование id не теряет знания, другой проект с прежним id
не получает чужую доску. Удаление/перезапуск сервиса не стирает знания.

Сам DevHub зарегистрирован собственным `devhub.json` под id `devhub` и каноническим
путём `F:/code/devhub`. Его Canvas и Kanban доступны в интерфейсе и MCP наравне с
остальными проектами. Манифест содержит пустой список сервисов: жизненным циклом
самого пульта управляет трей, а защита основной папки запрещает удалить её из пульта.

### MCP для агентов

Сервер запускается через stdio: `bun F:/code/devhub/src/mcp.ts` (`bun run mcp`).
Конфигурация также показана в **Настройки → Агенты / MCP**; `.mcp.json` подключает
сервер в совместимых клиентах для этого репозитория. Для всех проектов добавьте его
в пользовательские настройки своего MCP-клиента. Для Codex:

```powershell
codex mcp add devhub -- bun F:/code/devhub/src/mcp.ts
```

Для клиентов с JSON-конфигурацией:

```json
{ "mcpServers": { "devhub": { "command": "bun", "args": ["F:/code/devhub/src/mcp.ts"] } } }
```

| Инструмент | Назначение |
| --- | --- |
| `projects_list` | Проекты, id и канонические папки |
| `knowledge_read` | Вся доска проекта, текущая `revision`, время сохранения |
| `knowledge_search` | Поиск в блоках, связях, карточках и метках проекта |
| `knowledge_apply` | Атомарный пакет операций на прочитанной ревизии |

Операции: `canvas.node.put/delete`, `canvas.edge.put/delete`,
`kanban.column.put/delete`, `kanban.card.put/delete/move`. `put` заменяет целый
элемент; для новых элементов выбирайте уникальные id (например UUID). Для
`card.move` задаются `id`, `columnId` и необязательный `beforeId`; без `beforeId`
карточка становится последней в колонке. Схемы всех полей MCP выдаёт клиенту.

Обязательный рабочий цикл агента: до начала задачи найти проект по канонической
папке и прочитать его Canvas и Kanban через MCP; после работы, перед итоговым
ответом, перечитать актуальную ревизию и обновить обе доски. В Canvas сохраняются
решения, архитектура, ограничения и ссылки, в Kanban — результат задачи, проверки,
оставшаяся работа и блокеры. Завершённый статус ставится только после проверки.
Изменения записываются небольшим пакетом с полученной `revision`. Если версия изменилась,
перечитать и согласовать правку; повторять старый пакет с новой ревизией вслепую нельзя.
Удаление блока удаляет и его связи. Невалидный пакет не меняет ни одного элемента.
Лимиты проекта: 1000 блоков, 2000 связей, 30 колонок, 2000 карточек, 4 МБ JSON;
до 200 операций в одном пакете.

MCP не запускает dev-сервисы самостоятельно и не открывает базу: он использует
защищённый локальный API DevHub с машинным токеном; при необходимости поднимает сам
пульт через штатный launcher. API знаний: `GET /api/knowledge`,
`GET /api/knowledge/:id[?q=...]`, `POST /api/knowledge/:id` с
`{ revision, operations }`; чтение и запись требуют того же доступа, что страница
пульта или его локальный клиент. При конфликте API возвращает HTTP 409.

## Контракт разработки и production

Для создания проекта в другой базовой папке используйте
`bun run hub create python my-app --base-dir "D:/my projects"` (также доступны
шаблоны `bts` и `game2d`). Путь должен быть абсолютным. DevHub создаёт папку, назначает порты,
записывает `devhub.json` и сохраняет базовую папку в списке обнаружения проектов;
регистрация сохраняется после перезапуска пульта. HTTP `POST /api/create`
принимает ту же настройку в поле `baseDir`.

Devhub — единственный менеджер локальных dev-процессов. Основная папка проекта служит стендом
разработки и финальной проверки: `main` в режиме MVP, `stage` в режиме Прод. Каждый проект хранит `devhub.json`
с исходными командами сервисов, портами, зависимостями и группами запуска. `services.json` задаёт настройки
этого компьютера и папки `discover`; при старте пульт находит контракты соседних проектов.

```mermaid
flowchart LR
  Task[Worktree: codex/task] --> Merge[Интеграция и финальные проверки]
  Merge --> Stage[Основная папка: MVP main / Прод stage]
  Dev[dev / dev:server / dev:web] --> Launcher[Обёртка проекта]
  Launcher --> Hub[devhub: зависимости, PID, готовность, логи]
  Hub --> Stage
  Stage --> Service[Сервер разработки]
  Prod[Production: start / deploy / контейнер] --> App[Приложение]
```

- `bun run dev`, `npm run dev` и зарегистрированные dev-псевдонимы в приложениях передают запуск в пульт.
  Внутри монорепозитория работают и команды отдельных приложений. Повторный запуск возвращает уже
  управляемый сервис, предварительно восстанавливая и проверяя его зависимости; параллельные запросы не создают второй процесс.
- Linked worktree не включаются в каталог. Их dev-команды запускают основную папку; изменения
  становятся видны после интеграции. Процессный менеджер повторно проверяет основной checkout,
  ветку текущего режима и рабочую папку внутри проекта перед запуском. Старые самостоятельные копии
  перенаправляются через `aliases` в машинном `services.json`.
- `launch.dev` задаёт обычный состав проекта. Другие варианты запуска выбираются отдельно;
  несколько вариантов Expo или студии не запускаются одновременно одной кнопкой.
- `build`, production-`start`, `deploy` и production-контейнеры запускаются средствами самого приложения.
  Production не импортирует код devhub и не требует его установки. `start` Expo и `wrangler dev`
  относятся к разработке и тоже передают запуск в пульт.
- Процессы разработки получают `DEVHUB_ROOT`, `DEVHUB_SERVICE`, `DEVHUB_FRAME_ORIGIN`, `NODE_ENV=development`, UTF-8 и пути
  к исполняемым файлам пакетов. Production не получает эти настройки от пульта.
- Пульт ждёт готовности зависимостей и самого сервиса. Занятый порт и сервер, запущенный извне,
  требуют отдельного переноса: devhub не объявляет их своими и не останавливает автоматически.
- Исходные dev-скрипты сохранены в `.devhub/original-scripts.json`, обёртка — `.devhub/launch.cjs`.
  В Python-проектах есть `.devhub/dev.ps1` и `.devhub/dev.sh`; production CLI остаётся самостоятельным.

Пульт ищется рядом с проектами, через `DEVHUB_ROOT` или `~/.devhub.json`. `bun run install:client`
сохраняет путь к этому пульту; это нужно, например, проектам из `Documents/ChatGPT`.
После изменения `devhub.json` перезапустите сам пульт: `bun run hub reload` или пункт трея
«Перезапустить пульт». Запущенные им серверы сохраняются. `reload` передаёт трею просьбу
перезапустить пульт и ждёт, пока ответит новый; агенты вызывают его сами, когда этого требует задача.
Перезапуск из трея завершает только пульт и его оболочку запуска: Inference, её очередь,
исполнители и работающие задания продолжают работу. Новый пульт подхватывает прежние процессы.
В меню трея остаются только команды общей очереди; управление Montage и Modeler доступно на странице пульта.
Левый щелчок по значку открывает небольшое окно управления DevHub и Inference. Оно остаётся открытым
при пустой очереди или недоступном пульте; закрытие окна прячет его, сохраняя значок и работающие сервисы.
В окне можно запустить, остановить или перезапустить DevHub и управлять общей очередью Inference.
Выполняющиеся и ожидающие задания видны в порядке очереди. Длинный список прокручивается колёсиком
или полосой справа; заголовок и ресурсы остаются на месте. Для текущих заданий видны этап, измеренный
процент и шаги, для ресурсов — загрузка GPU/CPU и памяти. Данные обновляются раз в три секунды;
неизвестный прогресс не заменяется расчётным процентом. Веб-панель открывается отдельной кнопкой.
Открытая страница после перезапуска сохраняет текущую вкладку и продолжает получать данные.
Виджет «Пульт перезапущен» предлагает перезагрузить страницу; обновление происходит только по нажатию кнопки.

## Работа с worktree

В проекте доступны `bun run worktree create <task>`, `integrate <ref>`, `check`, `status`,
`publish`, `mode mvp|prod`, `finish <полный путь>`, `close <полный путь>` и `tidy [--apply [--kill]]`.
Общий CLI: `bun F:/code/devhub/src/stage.ts <команда> --project <путь|id>`.
Режим, проверки, release-ветка и место временных папок находятся в `.devhub/worktree.json`.

В MVP интеграция собственных изменений задачи идёт сразу в `main`; после финальных проверок
CLI пушит в настроенный remote и выполняет известную `deploy`-команду, если она задана.
Агент проверяет production-версию; разрешение владельца на MVP уже включает выпуск каждой задачи.
В Прод интеграция проходит в `stage`, а выпуск в `main` и прод требует явного разрешения задачи.
Все текущие проекты переводятся в MVP; выбрать Прод можно на странице управления проектом.
Существующая политика без `mode` остаётся Прод до явного переноса.

Прод требует чистые исходную и основную папки; MVP сохраняет непересекающиеся чужие локальные
правки и перед push проверяет как основную папку, так и чистый HEAD `main` в worktree.
Отметка проверки аннулируется при смене
режима, исходников или локального env; провал проверок блокирует публикацию.
Обычные worktree расположены в `F:/worktrees/<project>/<task>`, вне папок проектов `F:/code`.
После задачи `finish` удаляет рабочую папку и слитую ветку; `close` закрывает задачу без
интеграции и оставляет ветку как отложенную работу. Архивы не создаются.
Процессы, которые держат закрываемую папку, `finish`, `close` и `integrate` завершают сами; не
завершается только сеанс, из которого запущена команда: его пустую папку убирает уборка.
`bun run hub tidy [проект]` и страница «Порядок» показывают всё, что осталось после задач
в `F:/code`, `F:/worktrees` и `F:/AI`; `--apply` убирает слитые ветки, записи о worktree без папок
и пустые папки, а `--apply --kill` ещё и завершает процессы, которые держат такую папку.
Пустая папка без worktree, которой сутки не пользовались, уходит сама вместе с процессами,
которые её держат: это делают команды worktree для своего проекта и пульт раз в час (`tidy --idle`).
Имеющиеся локальные правки интегратор не включает в чужой commit и не публикует автоматически.
Подробный порядок и защита данных: [WORKTREES.md](WORKTREES.md).

`bun scripts/project-modes.ts` показывает перенос подключённых проектов в MVP; `--apply`
меняет политику и owner-блок инструкций с проверкой истории веток. Это не push и не deploy.

## Терминал

Из `F:/code/devhub`:

```text
bun run hub list
bun run hub check
bun run hub status
bun run hub start altay/site
bun run hub start luvclub
bun run hub stop altay/site
bun run hub restart altay/site
bun run hub reload
bun run hub logs altay/site --lines 50
bun run hub attach altay/site
bun run hub create bts my-app
bun run hub prod altay --logs
```

`--json` у `list` и `status` выдаёт машиночитаемый результат. `start` возвращает успех после готовности
сервиса; ошибка запуска или зависимости возвращает ненулевой код. `stop` и `restart` из CLI действуют
только на процессы пульта. `reload` перезапускает сам пульт через трей и возвращается, когда ответит
новый пульт; процессы проектов сохраняются. Логи находятся в `.logs`.

Готовность отдельного сервиса ожидается до пяти минут: первая компиляция Next.js на Windows может быть долгой. CLI ждёт действие до пятнадцати минут, включая последовательный запуск зависимостей. Завершившийся процесс или занятый порт возвращают ошибку сразу.

## Миграция локальных запусков

`bun run project:interfaces` показывает недостающие ссылки на проверенные веб-интерфейсы,
`bun run project:interfaces --write` добавляет их в `devhub.json` основных папок на `stage`.
Команда сохраняет пользовательские ссылки и проверки готовности, проверяет маршруты по исходникам
и блокирует конкурирующие stage-операции. Оригиналы и хеши записываются в
`.state/migrations/project-management-20261003/interfaces`. Повторный запуск без `--write`
должен показать `changes: 0`.

`bun run migrate` показывает план, `bun run migrate --write` применяет его. Скрипт повторяемый:
сохраняет первые исходные команды и не перезаписывает изменённую вручную команду без проверки.
Архивные копии, артефакты и GPU-инструменты, которыми управляет Inference, не становятся отдельными
серверами разработки. Для другой папки проектов используйте `--root PATH` и добавьте её в `discover`.

`bun run startup:migrate` показывает перевод автозапуска Predict Paper (задача планировщика
`predict-paper-runtime`) на пульт, `bun run startup:migrate -- -Apply` применяет его с резервной
копией задачи в `.state/startup-backup`. Восстановление: тот же PowerShell-скрипт с
`-Restore PATH -Apply`. Он меняет последующие запуски и не прерывает текущие процессы.
Очереди Inference свой автозапуск Windows не нужен: `inference/queue` и её удалённые исполнители
(`inference/executors`) — обычные сервисы пульта с `autostart`, они запускаются вместе с пультом.
Перезапускать очередь следует после окончания активных задач. Значение `Inference` в HKCU Run
запускало трей `inference.tray`, которого больше нет: скрипт его не читает и не пишет, а из прежней
резервной копии восстанавливает только задачу Predict Paper и сообщает, что значение пропущено.
Production-задачи и отдельные production-воркеры сохраняют свой запуск.
Прежний повторный запуск Predict Paper через 30 секунд перенесён в управляемый launcher:
`restart: "always"`, `restartDelayMs: 30000`. Для остальных сервисов перезапуск по умолчанию ручной.
Сервис теперь `predict/runtime`; исходники запускаются из `F:/code/predict`, прежний каталог
данных задаётся явно. DevHub запускает конечный `predict.runtime`, а подготовка через
`predict.local up` остаётся самостоятельным entrypoint приложения.

## Как открыть

- Ярлык «Пульт» на рабочем столе или левый щелчок по значку в трее (цветное кольцо) открывает небольшое
  окно управления. Кнопка «Веб-панель» в нём открывает страницу в браузере.
- Без трея: двойной щелчок по `Пульт.cmd`. Если пульт ещё не работает, он поднимется в фоне, без окна, и откроется
  страница http://127.0.0.1:4700/.
- Или в терминале, в этой папке:
  - `bun run open` — то же, что `Пульт.cmd`; с `--no-browser` только поднимает пульт;
  - `bun run start` — пульт в этом терминале;
  - `bun run dev` — для правки самого пульта: страница обновляется сама.

### Кто запускает пульт

Пульт и каждый запущенный им сервис наследуют окружение того, кто их запустил. У процессов настольных
приложений-агентов (Claude, Codex: это пакеты MSIX) своя копия `%LOCALAPPDATA%`: новые файлы попадают в
`%LOCALAPPDATA%\Packages\<пакет>\LocalCache\Local`, а уже лежащие там заслоняют настоящие. Windows при этом
не называет пакет у такого процесса, и окружение достаётся всем его потомкам. Сервис, запущенный оттуда,
расходится в данных с тем же сервисом, запущенным с рабочего стола: база, открытая с чужим устаревшим
журналом, оказывается повреждена. Поэтому в таком окружении пульт не работает.

- `bun run hub …`, `bun run open` и dev-обёртки проектов, застав пульт молчащим, сначала просят поднять его значок
  в трее (событие `Local\DevhubTray.Start`): значок работает в сеансе самого человека. Если значка нет или его
  пульт не появился за 15 секунд, команда поднимает пульт сама: из обычного терминала напрямую, а из
  приложения-агента через оболочку рабочего стола. Такой процесс становится дочерним для Explorer и видит
  настоящие папки. Когда и это не удалось, команда говорит об этом и пульт не запускает.
- Пульт, который уже запускается (его сервер отвечает, но он ещё осматривает компьютер: с десятками сервисов это
  около полуминуты), команда только ждёт, до полутора минут: вторая копия проиграла бы ему порт.
- Сам пульт при старте проверяет, чью `%LOCALAPPDATA%` он видит: создаёт в ней файл-пробу и ищет его в папках
  пакетов (`src/app-view.ts`). В копии приложения он не запускается и пишет причину в `.logs/hub.log`. Так же
  откажутся `bun run start` и `bun run dev` из сеанса агента.
- Значок, запущенный из приложения-агента (например, `bun run tray:install` в его сеансе), запускает себя заново
  через рабочий стол, а исходная копия завершается.
- Домашняя папка, `F:\` и `%TEMP%` во всех окружениях одни и те же. Уже работающий сервис остаётся в окружении,
  в котором стартовал: сменить его можно только перезапуском сервиса из пульта.

## Значок в трее, автозапуск и ярлык

`bun run tray:install` собирает маленькую программу `tray\bin\Пульт.exe` (компилятором C#, который есть в самой
Windows), кладёт ярлык «Пульт» на рабочий стол, включает запуск при входе в Windows и запускает значок.
Повторный запуск обновляет всё это; `bun run tray:uninstall` убирает значок, автозапуск и ярлык.

- Значок сам поднимает пульт и следит за ним: если пульт упал, через полминуты поднимает снова (три попытки за пять
  минут, потом говорит об этом и ждёт). Пока пульт не отвечает, кольцо серое.
- Пульт поднимает именно значок и тогда, когда его застала молчащим команда терминала или агент: она просит об этом
  событием `Local\DevhubTray.Start`, страница при этом не открывается. Просьба снимает и ожидание после трёх
  неудачных попыток. Подробнее — в разделе «Кто запускает пульт».
- Запущенный из приложения-агента значок не остаётся в его окружении: он запускает себя заново через рабочий стол
  (с параметром `--outside`). Если не вышло и это, он говорит об этом и не запускается.
- Левый щелчок по значку открывает окно управления DevHub и Inference. Правый открывает меню: состояние
  пульта, перезапуск, отдельная веб-панель, папка с логами, автозапуск и выход.
- Пока пульт работает, после его состояния в меню стоит общая очередь GPU и CPU: что с ней сейчас, «Открыть общую
  очередь», «Стоп общей очереди», «Пауза общей очереди», «Продолжить общую очередь». Команд Montage и Modeler
  в трее нет. «Стоп» и «Пауза» не прерывают работающие задания: новые не начинаются, пока очередь не продолжат.
  Эти пункты пульт присылает готовыми
  (`GET /api/queue/tray`), значок их только рисует и отправляет нажатия обратно; отказ очереди показывается
  всплывающим сообщением. Состояние очереди видно и в подсказке значка.
- «Выход» убирает значок и останавливает пульт; серверы проектов, запущенные из пульта, продолжают работать, и
  пульт найдёт их, когда его откроют снова.
- Ярлык на рабочем столе открывает пульт; если значка в трее ещё нет, он появится.
- Код программы — `tray\Tray.cs` и `tray\ControlWindow.cs`, скрипты установки — `scripts\install-windows.ps1`
  и `scripts\uninstall-windows.ps1`.

## Что на странице

Состав проектов и связи с данными описаны в [PROJECTS.md](PROJECTS.md).

- Слева все проекты и их сервисы. Цвет точки: зелёный — работает, запущен из пульта; синий — работает, но запущен
  не из пульта; жёлтый мигающий — запускается; оранжевый — порт занят, а сервис не отвечает как надо; оранжевый
  кружок — порт занят другим сервисом; красный — упал; серый — остановлен.
- «Обзор»: что работает сейчас; общая очередь; карточки проектов с кнопками запуска dev, остановки и удаления;
  базы в Docker с кнопками «Поднять» и «Остановить»; кто слушает какие порты.
- Карточка «Общая очередь» на «Обзоре» есть, когда проект объявил очередь в своём `devhub.json` (`queue`).
  Для генераций она показывает измеренный прогресс из Inference: этап, процент текущей операции
  и шаги. Те же данные видны в верхнем виджете и подробностях задания. Пока процент неизвестен,
  индикатор остаётся без числа; время работы и оценка длительности не превращаются в процент.
  Для нескольких заданий сохраняются отдельные индикаторы, общего расчётного процента нет.
  Названия этапов берутся из фиксированного списка; приватные описания, пути и узлы не передаются.
  В карточке:
  состояние словами; загрузка и температура видеокарты, видеопамять, свободная память и CPU; работающие задания —
  название, GPU или CPU и сколько оно идёт (приватное задание называется «Анонимное задание»); сколько заданий
  ждёт и чего. Кнопки «Стоп очереди» (с вопросом), «Пауза» и «Продолжить» делают то же, что пункты меню значка.
  У каждого парного исполнителя — состояние, его команды и «принимать заказы при запуске». Если очередь
  не отвечает, карточка говорит об этом и предлагает «Запустить», когда её сервис остановлен. «Панель очереди»
  открывает страницу сервиса с её собственной панелью.
- Страница проекта: режим MVP/Прод, основная папка, текущая ветка, основной интерфейс, dev-сервисы и удаление с диска.
  «Запустить dev» использует группу `launch.dev` из контракта проекта; альтернативные сервисы запускаются отдельно.
- Страница сервиса: его страницы прямо внутри пульта (H3/Qwen MediaPipes, студия сцен Montage…),
  лог в реальном времени и сведения: команда, папка, кто держит порт. Открытые страницы не перезагружаются при
  переключении вкладок. При проверке встраивания пульт учитывает свой адрес, порт и разрешённые CSP origins.
  Если сайт действительно запрещает встраивание, остаётся кнопка открытия в отдельной вкладке.

`DEVHUB_FRAME_ORIGIN` содержит точный HTTP origin работающего пульта, включая настроенный порт
или `--port`. Пульт задаёт его сам; переменная из конфигурации сервиса не может подменить этот адрес.
Приложение может разрешить этот origin и `localhost` на том же порту в `frame-ancestors` только
при управляемом dev-запуске. Самостоятельный production-запуск сохраняет собственную политику.
Встроенная страница использует свой API и прежнюю авторизацию; пульт не переписывает её заголовки.

## Избранное и сворачивание

Звёздочка в карточке, боковом списке или на странице проекта добавляет его в избранное. Избранные проекты
всегда отображаются первыми. По умолчанию избранные проекты раскрыты, остальные свёрнуты и в обзоре,
и в боковом списке. Звёздочка сразу применяет это правило к проекту в обеих областях. Карточки обзора
и группы бокового списка можно раскрывать и сворачивать независимо; ручной выбор сохраняется в браузере.
При сворачивании остаются название, состояние и ссылка на интерфейс. Ранее сохранённое избранное сохраняется.

## Удаление проекта

Кнопка «Удалить проект» есть в карточке и на странице проекта. Перед удалением пульт показывает точные
абсолютные пути: основную папку, существующие Git worktree и связанные копии из `services.json.aliases`.
Одно подтверждение удаляет содержимое всех перечисленных папок, включая локальные изменения и данные.
Процессы проекта, запущенные пультом, сначала останавливаются; список проектов обновляется сразу.

Общие Docker volumes и внешние папки, на которые указывают junction и символические ссылки, сохраняются.
Если другой проект использует удаляемый сервис или файлы, пульт показывает зависимость и блокирует удаление
до переноса данных и обновления конфигурации. Сам пульт, системные каталоги и корни коллекции защищены.
Дополнительный поиск ссылок в исходниках ограничен отдельно для каждого проекта: две секунды,
15 тысяч файлов и 128 МБ; файлы больше 2 МБ не читаются. Ошибки чтения и пределы этой проверки
показываются отдельными сворачиваемыми предупреждениями и не считаются найденными зависимостями.
Ссылки на удаляемые папки, зависимости сервисов и непроверенные bind mounts активного Compose
блокируют удаление. Содержимое моделей и данных не читается, вложенные junction проверяются отдельно.
Изменение папок или конфигурации после открытия диалога требует обновить список перед подтверждением.
Результат записывается в `.logs/actions.log`, состояние удаления — в `.state/deletions/<id>.json`.

## Как пульт запускает и останавливает

- Сервер запускается скрыто, без окна; всё, что он пишет, попадает в `.logs/<проект>-<сервис>.log`. Он живёт
  отдельно от пульта: пульт можно закрыть и открыть снова, он найдёт свои серверы.
  На Windows новый CMD запускает Explorer: его родителем не остаётся короткоживущий PowerShell.
  У каждой попытки свой batch и случайный маркер. Перед выполнением команды CMD оставляет квитанцию
  с PID, временем создания и точной командной строкой; пульт проверяет её, сохраняет владение и только
  затем разрешает запуск. Если квитанция не пришла за 20 секунд или запуск отменён, команда не выполняется.
  Коды выхода тоже относятся к конкретной попытке. Пульт проверяет время создания и маркер при наблюдении,
  повторном подключении и остановке, в том числе без открытой страницы. Старые запуски сохраняются до
  обычного перезапуска и перед остановкой проверяются по точному пути batch. Метаданные завершённых попыток
  удаляются при следующем запуске; неподтверждённые живые процессы сохраняются для разбирательства.
- Перед запуском пульт поднимает то, что сервису нужно: другие сервисы и базы в Docker (например, Postgres Montage).
  Если порт уже занят, сервис не запускается, а пульт говорит, кто этот порт держит.
- Сервисы с `autostart` пульт запускает сам, когда стартует: по порядку каталога, каждый после того, что ему нужно.
  Страница и CLI этого не ждут. Сервис, который уже работает из пульта, остаётся как есть; чужой процесс на его
  порту не останавливается — запуск не удаётся, и об этом есть строка «автозапуск» в `.logs/actions.log`.
- Если неожиданно завершился сам launcher сервиса, пульт восстанавливает его по `restart` и `restartDelayMs`,
  даже без открытой страницы. Повтор проходит обычную проверку зависимостей и владельца порта; оставшийся
  дочерний или чужой процесс не завершается. Ручная остановка отменяет ожидающий повтор; у `on-failure`
  нормальный выход с кодом 0 тоже не вызывает повтор. Автозапуск при старте пульта действует по-прежнему.
  Состояние остановки/паузы очереди Inference восстановление сервисов не меняет.
- «Остановить» гасит сервер вместе со всем, что он запустил. Сервер, запущенный не из пульта, и контейнеры Docker
  останавливаются только после вопроса.
- Каждое нажатие и его итог записываются в `.logs/actions.log`.
- Пока страница пульта не открыта, он никого не опрашивает, только следит за своими серверами. С открытой
  страницей спрашивает проверку здоровья сервисов раз в 10 секунд, чтобы не засорять их логи.

## Пересекающиеся порты

Несколько проектов и их рабочие копии используют 3000 для API, 3001 для веб-интерфейса и 5432 для Postgres.
Например, 3000 используют Montage, Modeler, Luv Club, CRM Земстрой и Gameradar. Пульт резервирует порт на время
запуска и отказывает следующему сервису, если порт уже занят; владелец показан на странице сервиса.
Порты контрактов согласованы с текущими числовыми настройками приложений. Для совместного запуска проектов
задайте отдельные порты в devhub.json вместе с адресами API и CORS соответствующего приложения.

## Как добавить сервис

Создайте `devhub.json` в корне проекта. Проект: `id`, `name`, при необходимости
`compose` — файл Docker Compose, имя проекта в Docker и какие его сервисы нужны для разработки. Сервис:

- `id`, `name`, `description`;
- `command` — чем запускать; без неё пульт только следит за сервисом;
- `port` и `health` — адрес, который отвечает, когда сервис готов;
- `ui` — страницы сервиса: подпись и путь;
- `needs` — что поднять раньше: `проект/сервис` или `docker:<имя проекта в Docker>`;
- `env`, `cwd` — переменные и папка внутри проекта;
- `warn` — что сказать перед запуском (тратит деньги, держит видеокарту, нужен секрет…).
- `restart`, `restartDelayMs` — политика повторного запуска: `never`, `on-failure` или `always` и пауза.
- `autostart` — `true`, если сервис должен работать всегда: пульт запускает его вместе с собой.
- `queue` — сервис принадлежит общей очереди GPU и CPU этого компьютера, и пульт показывает её на «Обзоре» и в меню
  значка: `"queue": { "role": "queue", "tokenFile": "runtime/api-token" }`. `role` — `queue` у самой очереди
  (её локальный API на `port`) или `executors` у хоста её удалённых исполнителей; каждая роль объявляется один раз
  на весь каталог. `tokenFile` — файл с токеном этого API внутри папки проекта.

`compose.overrides` перечисляет файлы разработки после основного Compose-файла. Например,
Gameradar использует `docker-compose.dev.yml`, чтобы открыть базы локальному dev-серверу;
пульт поднимает только `postgres` и `redis`, без production-приложения.

`launch` сопоставляет публичную команду со списком сервисов, например
`"launch": { "dev": ["server", "web"], "dev:server": ["server"] }`.
`cwd` задавайте относительно корня проекта. Корень определяется по расположению контракта;
абсолютные пути к другим компьютерам в контракт не добавляйте. Dev-обёртку можно взять из
`templates/launch.cjs`. `services.json` поддерживает старые явные записи, но контракт проекта
заменяет старую запись с тем же `id`.

Пульт читает список при запуске; после правки выполните `bun run hub reload`.

## Безопасность

- Пульт слушает только 127.0.0.1 и отвечает только на своём адресе; кнопки работают только с его собственной
  страницы.
- Управление сервисами запускает те же команды, что вы запустили бы в терминале. Сервисы,
  которые тратят деньги (MediaPipes для Montage на RunPod) или держат видеокарту (очередь Inference), помечены
  предупреждением.
- Токен API общей очереди пульт читает из файла её проекта при каждом запросе и отправляет только её сервисам
  на этом компьютере; на страницу и в значок он не попадает. О задании очереди пульт передаёт только номер,
  название, ресурс и время начала — без команды, workflow, результата и ошибки.

## Агенты работают через пульт

Claude Code, Codex и другие агенты запускают dev-серверы только через DevHub:
`bun F:/code/devhub/src/cli.ts start|stop|restart|status|logs|attach`. `bun run agents` показывает план,
`bun run agents --write` применяет его:

- правила владельца целиком — в файлах, общих для всей машины: `F:/code/AGENTS.md` (над проектами),
  `F:/worktrees/AGENTS.md` (над их worktree), `~/.claude/CLAUDE.md` и `~/.codex/AGENTS.md`. Это блоки
  `DEVHUB:DEV-SERVER` (dev-серверы и команды пульта), `DEVHUB:WORKTREE-POLICY` (режимы, worktree, порядок),
  `DEVHUB:PROJECT-KNOWLEDGE` (чтение знаний перед задачей и обновление Canvas и Kanban через MCP после неё)
  и правила, которые проект объявляет для всей машины: их текст хранится в AGENTS.md этого проекта
  (сейчас `INFERENCE:QUEUE-PAUSE` из Inference) и только копируется оттуда. Остальной текст файлов сохраняется;
- hook `PreToolUse` в `~/.claude/settings.json` (`src/agent-guard.ts`): внутри проекта с `devhub.json`
  он отклоняет `next dev`, `vite`, `bun --hot`, `node --watch`, `turbo dev`, `uvicorn --reload`, `expo start`
  и подобные команды, а также `preview_start` для записи `.claude/launch.json`, которая запускает сервер сама.
  Сборки, тесты и `bun run dev` проходят; при ошибке hook ничего не блокирует;
- с `--projects` — в AGENTS.md и Cursor-правиле каждого проекта вместо копии правил остаётся короткая
  ссылка на них (основная папка, её `.devhub/worktree.json`, где читать правила): смена правила больше не
  правит ни один репозиторий и ни один worktree. Эту правку DevHub коммитит сам, под блокировкой проекта;
  если в файле есть чьи-то ещё изменения или проект занят интеграцией, файл остаётся как есть и
  коммитится следующим запуском. Push не выполняется: коммит уходит со следующим выпуском проекта;
- там же — `.claude/launch.json`, где превью запускается через `cli.ts attach <проект>/<сервис>`: сервис
  стартует в пульте, а команда только показывает его лог. Конфигурация проекта, которая уже идёт через
  DevHub, не переписывается; прежняя с самостоятельным запуском сохраняется в
  `.devhub/original-claude-launch.json`.

`logs <проект>/<сервис> [--lines N]` печатает конец лога из `.logs`, `attach` запускает сервис и следит
за логом; Ctrl+C отключает только вывод.

## Новый проект

«+ Новый проект» в боковом списке или `bun run hub create bts|python|game2d ИМЯ [--description ТЕКСТ] [--no-web]`.
Проект создаётся в папке `code` из `services.json` и сразу появляется в пульте:

- **Better-T-Stack** — `create-better-t-stack create-json`: Next.js, Hono на Bun, tRPC, Better Auth,
  Drizzle + Postgres в Docker, Turborepo, Biome/Ultracite, lefthook, evlog, skills и MCP, Dockerfile для
  web и server. Как у analytics и brains.
- **Python** — чистый проект на uv: пакет в `src/`, pytest, ruff; по умолчанию FastAPI с `/health`
  и Dockerfile, с `--no-web` — пакет без dev-сервиса.
- **2D-игра** (`game2d`) — браузерная игра на Phaser, Vite и TypeScript: игровая сцена,
  масштабирование экрана и локальное сохранение. `bun run build` создаёт статический сайт в `dist/`;
  запуск разработки идёт через DevHub. Например: `bun run hub create game2d prapor-idle`.

Пульт выбирает свободные порты (приложения с 3020, Postgres с 5433, Python API с 8100), пишет их в
`devhub.json`, `.env` и `docker-compose.yml`, заменяет dev-скрипты обёртками, сохраняет исходные в
`.devhub/original-scripts.json`, создаёт политику MVP с `remote: null`, AGENTS.md с правилами,
`.claude/launch.json` и первый коммит в `main`. Remote, Coolify и деплой подключаются отдельно.
Если код шаблона ещё не проходит Ultracite, `bun run check` не входит в финальные проверки,
пока замечания не исправлены.

## Прод (Coolify)

[Зеркала сервисов delopusk.ru](DELOPUSK-MIRRORS.md): CRM, Алтай, GameRadar и
общая Grafana открываются с доменов `*.balkhaev.com` через управляющий сервер.
Прокси обращается к тем же production-приложениям и данным; там описаны адреса,
ограничения, конфигурация и процедура выкладки без SSH-доступа к исходному серверу.

Раздел «Прод» и блок на странице проекта показывают, что работает в Coolify: статус и домены приложений,
коммит, последние деплои, логи, базы и сервисы проекта, ссылки в консоль Coolify. Пульт только читает:
он не деплоит и не перезапускает. В терминале: `bun run hub prod [проект] [--logs] [--lines N] [--json]`.

```json
"coolify": { "url": "https://deploy.balkhaev.com", "tokenEnv": "COOLIFY_ACCESS_TOKEN", "links": {} }
```

Токен берётся из переменной окружения (на Windows также из пользовательских переменных) и не уходит
на страницу; страница получает только выбранные поля без секретов, переменных и логов сборки.
Приложения сопоставляются с проектами по git-репозиторию, затем по имени проекта Coolify;
`links` задаёт явную связь: `"montage": ["<uuid приложения>", "<имя проекта Coolify>"]`.

## Проверка кода

`bun run check` — типы и Ultracite; `bun test` — проверки конфигурации, discovery, CLI, делегирования,
готовности, владения процессами и конкурентного запуска. `bun run hub check` проверяет контракты
всех подключённых рабочих каталогов.
